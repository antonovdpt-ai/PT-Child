# История проведённых занятий

## Как работает синхронизация

Визит из расписания создаёт строку в `sessions` в транзакции сохранения. `appointments.session_id` связывает визит с записью, а уникальный индекс запрещает использовать одну запись для нескольких визитов. Время берётся из `starts_at`, дата рассчитывается в часовом поясе, сохранённом при записи или переносе визита. Для записей без известного исходного пояса действует `Europe/Moscow`. Проверьте этот пояс при сверке старых визитов. Расписание по-прежнему показывает время устройства. Карточка подписывает часовой пояс времени визита, если он отличается от пояса устройства.

После отмены, неявки или возврата в план история скрывает запись по `voided_at`. Повторная отметка «Проведено» восстанавливает её вместе с описанием. Для исправления пациента отмените ошибочный визит и создайте новый. Если визит требуется исключить с возможностью восстановления, используйте смену статуса. Удаление визита сохраняет его клиническую запись в базе, но восстановление из интерфейса требует сохранённой связи с расписанием.

ИИ получает активные записи с наблюдениями, функциональными изменениями или явной оценкой. Одна отметка «Трудно оценить» без наблюдений не считается описанием. Суммарное число активных визитов передаётся отдельным полем. В форме автоматического занятия сохранённый план можно прикрепить вручную, чтобы при заполнении старого визита случайно не перенести в него будущий план.

## Порядок внедрения после разрешения

1. Проверить миграцию и обновлённые приложение и `ptchild-ai` на тестовой базе с синтетическими данными. Проверить статус, перенос через полночь, отмену, восстановление, привязку нового первичного визита, оплату и отчёт для родителя. Подтвердить, что приложение и Edge Function направлены на тестовую базу.
2. Перед работой с целевой базой проверить резервную копию и возможность восстановления. Выполнить предварительные проверки связей ниже. Если найден конфликт, разобрать его по источникам и согласовать исправление, прежде чем повторять попытку.
3. В согласованное окно применить `20261112_008_auto_session_history.sql`, дождаться обновления схемы PostgREST, затем выпустить `ptchild-ai` и frontend из одной версии. Миграция добавляет поля и индексы в существующие таблицы. PostgreSQL пересчитывает вычисляемое поле клинических данных для существующих строк `sessions`, поэтому оцените блокировки и длительность на копии базы. Старый браузерный код не может подтвердить визит через обновлённый RPC без признака явного подтверждения. Попросить специалистов обновить открытые вкладки после выпуска.
4. Проверить рабочий интерфейс и схему разрешённым способом. Для записи синтетических данных использовать согласованное тестовое окружение. При проблеме остановить выпуск и зафиксировать состояние схемы, Edge Function и фронтенда. Восстановление кода выполнять совместимой версией, в которой браузер не подтверждает визиты по дате. Сохранить строки `sessions`, связи и отметки исключения при любом откате.
5. Отдельно провести сверку истории по процедуре ниже. Применение миграции не запускает её.

### Предварительные проверки связей

Оба запроса должны вернуть ноль строк. Результаты сверки остаются в авторизованной консоли.

```sql
select session_id, count(*)
from public.appointments
where session_id is not null
group by session_id
having count(*) > 1;

select a.id, a.session_id
from public.appointments a
join public.sessions s on s.id = a.session_id
left join public.patients p on p.id = a.patient_id
where a.kind <> 'appointment'
   or a.patient_id is distinct from s.patient_id
   or a.therapist_id is distinct from s.therapist_id
   or a.therapist_id is distinct from p.therapist_id;
```

### Однократная сверка

1. Запустите `session-history-audit.sql` после миграции. Результат содержит идентификаторы, версии строк, время и кандидатов среди ручных записей. Сохраните отчёт во внутренней консоли. Совпадение даты и ребёнка служит подсказкой, поскольку в один день могло быть несколько занятий.
2. По каждому визиту подтвердите факт проведения и часовой пояс. Старая версия календаря могла автоматически отмечать запланированные визиты проведёнными, включая первичные визиты без карточки. Уже существующие точные связи тоже появятся в отчёте. Пока их метаданные не синхронизированы, ранее созданные записи отображаются как ручные. Если соответствие спорное или факт визита не подтверждён, оставьте строку на ручной проверке.
3. Для подтверждённого визита укажите точный ID существующего занятия или `NULL`, если проверка подтверждает, что занятия в истории нет. Заполните в копии `session-history-apply.sql` временную таблицу `session_history_review`. Возьмите статус, время и версии строк из проверки. В `schedule_timezone` укажите подтверждённый пояс. Скрипт проверяет актуальность данных под блокировкой и завершает пробный запуск через `ROLLBACK`.
4. Просмотрите результат пробного запуска. Только после отдельного согласования этого списка примените его через `COMMIT`. Если запись поменялась после проверки, заново проверьте соответствие. Повтор уже применённого согласованного списка не создаёт дубликаты.
