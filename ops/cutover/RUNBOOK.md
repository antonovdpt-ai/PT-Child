# Fizira production cutover: managed Supabase → российский self-hosted Supabase

Эта процедура относится к C21. Она не должна запускаться как обычное
обновление frontend. До начала должны быть закрыты C07–C09, C13, обязательные
части C15 и согласовано окно обслуживания.

## Стоп-условия

Cutover запрещён, если выполняется хотя бы одно условие:

- последняя полная резервная копия не имеет результата восстановления `PASS`;
- Windows pull-backup не подтверждён после последнего существенного изменения;
- нет отдельного проверенного backup исходного managed Supabase;
- неизвестен владелец окна обслуживания и решения об откате;
- российский Auth/SMTP, Storage, Edge Functions или TLS имеют ошибку;
- нельзя запретить запись в старый backend на время финальной синхронизации;
- нет актуальных publishable/anon key российского backend;
- не подготовлены два синтетических специалиста для проверки изоляции.

## Секреты

Не передавать URL с паролями в аргументах команд и не сохранять их в Git.
Для `psql` создать root-only `pg_service.conf` с сервисами `fizira-source` и
`fizira-target`. Путь можно передать через `PGSERVICEFILE`; файл должен иметь
права `600`.

## 1. До окна обслуживания

1. Зафиксировать SHA текущего `main`, текущий `SUPABASE_URL` и клиентскую
   версию из `index.html`.
2. Сделать и восстановить полный российский backup через `ops/backup`.
3. Сделать независимый backup managed source: Auth, прикладные схемы, Storage,
   конфигурация, список Edge Functions.
4. Проверить свободное место, TLS `auth.fizira.com`, SMTP и статус контейнеров.
5. Проверить вход, recovery, загрузку/чтение/удаление файла и четыре ИИ-сценария
   на синтетических данных российского target.
6. Подготовить cutover-коммит, меняющий одновременно URL, publishable/anon key
   и версию клиента. Не сливать его заранее.

## 2. Freeze

1. Включить страницу обслуживания или серверный запрет всех изменяющих
   операций на managed source.
2. Дождаться завершения активных запросов.
3. Записать точное UTC-время начала freeze.
4. Убедиться прямым запросом, что старый клиент больше не может создавать или
   изменять пациента, занятие и файл.

Одного сообщения пользователям недостаточно: запрет должен действовать на
backend, иначе открытая ранее вкладка продолжит писать в старую базу.

## 3. Финальная синхронизация

Перед окном обслуживания запустить на self-hosted сервере интерактивную
read-only обёртку от `root`:

```bash
./ops/cutover/run-readonly-preflight.sh
```

Она скрыто запрашивает пароль исходной managed Supabase, держит его только в
окружении процесса, проверяет оба подключения и запускает сверку. Если прямой
адрес БД недоступен, нужно взять Session pooler host, port и user из Supabase
Dashboard → Connect. Пароль нельзя вставлять в команду или историю shell.

Успешный предварительный результат содержит оба маркера:

```text
CUTOVER_DATABASE_PARITY_OK
READONLY_PRODUCTION_PREFLIGHT_OK evidence=...
```

Обёртка и базовый preflight выполняют только `SELECT`.

1. Повторно перенести Auth с сохранением UUID и password hashes.
2. Перенести все прикладные таблицы с PK/FK и sequence state.
3. Синхронизировать оба Storage bucket и физические объекты.
4. Применить целевые миграции безопасности и Edge Functions.
5. Выполнить физическую проверку Storage через `rclone check` или эквивалент с
   размером и checksum каждого объекта.
6. Запустить сверку БД:

   ```bash
   PGSERVICEFILE=/root/.pg_service.conf \
     FIZIRA_SOURCE_PGSERVICE=fizira-source \
     FIZIRA_TARGET_PGSERVICE=fizira-target \
     FIZIRA_CUTOVER_OUTPUT_DIR=/root/fizira-cutover-evidence \
     bash ops/cutover/preflight.sh
   ```

Обязательный результат: `CUTOVER_DATABASE_PARITY_OK`. Скрипт выводит только
количества и digest строк, а не персональные данные.

## 4. Переключение клиента

1. Слить заранее подготовленный cutover-коммит.
2. Дождаться публикации `app.fizira.com` и принудительно обновить страницу.
3. Проверить в загруженном `app.js`, что `SUPABASE_URL` равен
   `https://auth.fizira.com`, а старый project ref отсутствует.
4. Проверить отсутствие ошибок модулей и CORS в браузере.

## 5. Smoke-test после переключения

Использовать только синтетические данные:

- новый специалист: регистрация, подтверждение почты, вход, logout, recovery;
- существующий специалист: вход после миграции и сохранённый UUID;
- создание/редактирование/удаление пациента;
- оценка, цель, занятие, отчёт и PDF;
- загрузка, просмотр и удаление изображения и документа;
- четыре ИИ-сценария;
- удаление пациента и полный synthetic account-deletion test;
- два специалиста и аноним не видят чужие строки и Storage paths;
- старый managed backend остаётся недоступным для записи.

После `PASS` открыть доступ ограниченно, наблюдать ошибки Auth/DB/Storage и
только затем снять обслуживание полностью.

## 6. Rollback

Rollback разрешён только до появления новых production-записей в российском
backend. Если новые записи уже появились, простое возвращение старого URL
потеряет их и запрещено.

До появления новых записей:

1. снова включить обслуживание;
2. вернуть предыдущий клиентский commit;
3. подтвердить, что managed source всё ещё заблокирован или осознанно снова
   открыт для записи;
4. зафиксировать причину, время и результаты проверки.

После появления новых записей нужен отдельный обратный перенос или исправление
target на месте. Решение принимает назначенный владелец инцидента.

## 7. Закрытие managed Supabase

Не удалять старый проект сразу после cutover. Сначала:

1. сохранить утверждённый backup и доказательство сверки;
2. отозвать service-role, SMTP, Storage и CI-секреты старого проекта;
3. исключить старый project ref из frontend, Actions и документации;
4. выдержать утверждённый юридический срок;
5. удалить или обезличить зарубежную копию по согласованной процедуре;
6. оформить акт с датой, ответственным и перечнем удалённых копий.
