# Fizira — кабинет родителя: техническая спецификация первой версии

Дата: 2026-10-02  
Ветка: `codex/parent-portal`  
Статус: согласованная архитектурная основа; реализация не начата.

## 1. Контекст и источник истины

Публичный frontend production развернут из репозитория `antonovdpt-ai/PT-Child`. На момент аудита:
- актуальная ветка `main`: `f9f4220`;
- ручная доставка frontend для этого SHA завершилась успешно 1 октября 2026;
- последующие public production smoke-проверки завершились успешно;
- production загружает frontend-маркер `0.169-legal-release`.

Любые изменения начинаются от `main`; production не перезаписывается старой версией. Миграции БД и Edge Functions не запускаются из frontend-deploy workflow и требуют отдельного контролируемого релиза.

## 2. Цель и границы MVP

Цель: дать родителю безопасный, mobile-first кабинет, отвечающий на вопрос: «что происходит с терапией ребёнка, что мы делаем и есть ли прогресс».

В первой версии родитель может:
1. принять одноразовое приглашение, создать пароль и войти;
2. переключаться между явно назначенными детьми;
3. видеть ближайшее занятие и список занятий;
4. читать только утверждённый первичный отчёт;
5. читать опубликованные отчёты занятий и выбранные фотографии;
6. видеть опубликованные цели, безопасную динамику и внутренние уведомления;
7. открывать профиль, менять пароль и выходить.

Не входят в MVP: чат, видеосвязь, платежи, самостоятельная запись, редактирование карты, домашние программы, автогенерация рекомендаций для родителя, push-уведомления.

## 3. Принцип безопасности

Интерфейс не является границей безопасности. Родитель не получает SELECT-доступ к исходным таблицам клинической карты: `patients`, `assessments`, `sessions`, `goals`, `patient_media`, `parent_reports` в полном виде.

Вместо этого:
- исходные данные остаются доступны специалисту через существующие RLS-политики;
- данные для родителя становятся доступны только после явной публикации;
- родитель получает безопасные проекции только через ограниченные RPC-функции и Edge Functions;
- каждая функция проверяет `auth.uid()`, активную связь parent→child и статус публикации;
- приватное Storage не открывается родителю напрямую: короткоживущие signed URL выдаёт backend после проверки конкретного опубликованного объекта.

Это исключает получение чужих данных заменой UUID, URL, storage path или вызова PostgREST напрямую.

## 4. Роли и доступ

### 4.1 Роли

Добавить таблицу `app_user_roles`:

| Поле | Назначение |
|---|---|
| `user_id` | FK на `auth.users` |
| `role` | `specialist` или `parent` |
| `created_at` | аудит назначения роли |

Первичный ключ: `(user_id, role)`. Модель допускает, что один пользователь может быть и специалистом, и родителем. Существующим учетным записям в миграции назначается `specialist`.

Клиент не получает права создавать или менять роли. Роль `parent` назначается только безопасной функцией принятия приглашения.

### 4.2 Привязка родителя к ребёнку

Добавить `parent_child_access`:

| Поле | Назначение |
|---|---|
| `id` | UUID |
| `parent_user_id` | родитель из `auth.users` |
| `patient_id` | ребёнок |
| `therapist_id` | владелец ребёнка на момент предоставления доступа |
| `contact_id` | исходный контакт семьи, если есть |
| `status` | `active` или `revoked` |
| `granted_at`, `revoked_at`, `revoked_by` | аудит |

Уникальность: один активный доступ на пару `parent_user_id + patient_id`. Отзыв не удаляет аудитную запись.

Специалист видит и управляет доступом только у своих детей. Родитель не имеет прямых прав на изменение связи.

## 5. Приглашения и регистрация

### 5.1 Данные контакта

К `patient_contacts` добавить `email` (nullable для обычного контакта, обязательный только при приглашении). Email нормализуется в нижний регистр на сервере.

### 5.2 Таблица приглашений

Добавить `parent_invitations`:

| Поле | Назначение |
|---|---|
| `id` | UUID приглашения |
| `patient_id`, `therapist_id`, `contact_id` | контекст приглашения |
| `email_normalized` | адрес получателя |
| `token_digest` | SHA-256 случайного токена; сырой токен не хранится |
| `expires_at` | срок действия, по умолчанию 7 дней |
| `accepted_at`, `accepted_by` | одноразовое принятие |
| `revoked_at`, `revoked_by` | отзыв/замена |
| `created_at` | аудит |

Повторное приглашение отзывает предыдущее активное приглашение этого контакта и создаёт новое.

### 5.3 Поток

1. Специалист нажимает «Пригласить в кабинет родителя».
2. Edge Function `create-parent-invitation` проверяет специалиста, контакт, ребёнка и email, создаёт приглашение и отправляет письмо через уже настроенные Supabase Auth + SMTP Timeweb.
3. В ссылке есть случайный токен и URL `parent.html`; токен одноразовый, а ссылка Auth также имеет срок действия.
4. Новый родитель задаёт имя, пароль, подтверждение пароля и принимает юридические документы. Существующий пользователь подтверждает вход через письмо.
5. `accept_parent_invitation` сверяет хеш токена, срок, статус, email текущего пользователя и привязку контакта; атомарно создаёт роль `parent`, связь `parent_child_access` и помечает приглашение принятым.
6. После успешного принятия токен удаляется из адресной строки через `history.replaceState`.

Ошибки «истекло», «уже использовано», «отозвано», «другой email» объясняются человеку без раскрытия данных ребёнка.

## 6. Публикация данных

### 6.1 Первичный отчёт

Существующая таблица `parent_reports` сохраняется и расширяется:
- `publication_status`: `draft`, `publishing`, `published`, `publication_error`, `archived`;
- `published_at`, `published_by`;
- `published_snapshot jsonb`;
- `pdf_storage_path`;
- `pdf_generated_at`.

Все ранее сохраненные отчёты мигрируют в `draft`, а не публикуются автоматически.

Публикация создаёт неизменяемый безопасный snapshot. До успешной генерации PDF статус `publishing`; при ошибке он не виден родителю и специалист может повторить операцию.

### 6.2 Отчёт занятия

Добавить `parent_session_reports` — отдельную сущность, потому что она отличается от первичного отчёта и не является дубликатом медицинской записи:

| Поле | Назначение |
|---|---|
| `id`, `patient_id`, `session_id`, `therapist_id` | связи |
| `what_did`, `what_worked`, `attention`, `home_recommendations` | текст только для родителя |
| `publication_status`, `published_at`, `published_by` | публикация |
| `published_snapshot`, `pdf_storage_path` | неизменяемая версия и PDF |

Внутренняя `sessions.note`, AI-черновики, `planned_session`, tolerance и служебные поля не копируются и не публикуются автоматически.

### 6.3 Фотографии

Добавить `parent_session_report_media`:
- `parent_session_report_id`;
- `patient_media_id`;
- `position`;
- `created_at`.

Сопоставление проверяет, что фото и отчёт принадлежат одному ребёнку и одному специалисту. Фото доступно родителю только если отчёт имеет `publication_status = published` и фото явно выбрано в этой таблице. Поврежденный или недоступный файл отображается как «Фото недоступно».

### 6.4 Цели

Не открывать родителю строку из `goals`, поскольку она содержит рабочие поля специалиста. Добавить `parent_goal_publications`:

| Поле | Назначение |
|---|---|
| `goal_id`, `patient_id`, `therapist_id` | исходная связь |
| `title`, `description` | упрощённое родительское изложение |
| `status` | `new`, `in_progress`, `achieved`, `revised` |
| `published_at`, `unpublished_at`, `updated_at` | явное управление |

Искусственный процент не отображается. Изменение статуса/текста публикуется специалистом явно.

### 6.5 Динамика

Динамика строится только из:
- опубликованных целей;
- дат и значений реально использованных `standardized_assessments` (GMFM-66, HINE, MACS, CFCS, EDACS);
- вручную опубликованной формулировки специалиста в цели или отчёте.

Не передавать родителю поля `note` стандартизированной оценки и не генерировать клинические выводы автоматически. Для категориальных шкал выводится timeline значений; линейный график используется только для корректных числовых рядов.

## 7. PDF и файлы

Каждый опубликованный отчёт получает PDF после подтверждения специалистом:
1. backend генерирует PDF из `published_snapshot` с внедренным кириллическим шрифтом;
2. сохраняет его в закрытом `patient-media` или отдельном закрытом префиксе отчётов;
3. хранит путь только в записи опубликованного отчёта;
4. Edge Function `parent-report-file` выдаёт signed URL сроком до 5 минут исключительно после проверки доступа.

В кабинете родителя доступны просмотр и скачивание утвержденного PDF. PDF не пересоздаётся из текущей внутренней карточки, поэтому последующая правка заметок специалиста не изменит уже опубликованный документ.

## 8. Backend и RLS

### 8.1 RPC

Добавить security-definer функции с фиксированным `search_path`, явным `auth.uid()` и запретом доступа `anon`:
- `accept_parent_invitation(token, accepted_documents)`;
- `parent_portal_children()`;
- `parent_portal_dashboard(patient_id)`;
- `parent_portal_schedule(patient_id, mode)`;
- `parent_portal_reports(patient_id)`;
- `parent_portal_report(report_id)`;
- `parent_portal_goals(patient_id)`;
- `parent_portal_dynamics(patient_id)`;
- `parent_portal_notifications(patient_id)`;
- `parent_mark_notifications_read(ids)`.

Каждая функция возвращает только разрешённые поля и вызывает единый helper `parent_has_active_access(auth.uid(), patient_id)`.

### 8.2 Edge Functions

Добавить:
- `create-parent-invitation`;
- `resend-parent-invitation`;
- `revoke-parent-access`;
- `generate-parent-report-pdf`;
- `parent-report-file`.

Service-role ключ используется только внутри Edge Function/Timeweb окружения и никогда не попадает в frontend, GitHub или URL.

### 8.3 RLS

- Существующие source-table RLS сохраняются для специалиста.
- Для родителя не добавляются SELECT-политики на клинические source tables.
- Таблицы приглашений/связей доступны специалисту только для собственных пациентов; родителю — только через безопасные функции или свои минимальные status-проекции.
- Все INSERT/UPDATE публикаций проверяют принадлежность ребёнка специалисту.
- Storage-политики не расширяются для родителя; доступ только через signed URL от проверенной Edge Function.

## 9. Уведомления

Добавить `parent_notifications`:
- `parent_user_id`, `patient_id`;
- `type`, `title`, `body`;
- `entity_type`, `entity_id`;
- `created_at`, `read_at`.

Уведомления создаются при публикации отчёта/цели и при значимом изменении занятия (создание, время, статус). Оплата и финансовые поля не создают уведомлений и никогда не попадают в parent API.

## 10. Интерфейс

### 10.1 Структура

Новые файлы:
- `parent.html` — отдельная точка входа;
- `parent.js` — родительский UI и работа только с parent RPC;
- `parent.css` — mobile-first дополнения к существующей дизайн-системе;
- `parent-domain.mjs` — чистые функции форматирования/состояний для unit-тестов;
- `parent-specialist.js` — небольшой модуль публикации и приглашений в интерфейсе специалиста.

В `index.html/app.js` добавляется role-aware redirect: пользователь с ролью parent не загружает список пациентов специалиста; при попытке открыть его направляется в `parent.html`. Пользователь с обеими ролями может осознанно переключать контур через меню.

### 10.2 Родительский кабинет

Mobile-first dashboard:
- верхняя панель Fizira, ребёнок, возраст, переключатель детей, профиль;
- карточки: ближайшее занятие, цели, последнее опубликованное занятие, динамика, «Новое»;
- нижняя навигация: Главная, Расписание, Отчёты, Цели, Динамика;
- desktop: компактная боковая/верхняя навигация в существующем стиле Fizira.

Состояния: skeleton при загрузке, понятные empty states, retry при ошибке, «Фото недоступно», отсутствие финансовых и клинических служебных данных.

### 10.3 Кабинет специалиста

В карточке ребёнка появляется вкладка «Кабинет родителя»:
- список контактов с email и статусом: не приглашён / приглашение отправлено / активирован / доступ отозван;
- действия: пригласить, повторить приглашение, отключить доступ;
- сводка видимости: первичный отчёт, последний отчёт занятия, цели, число опубликованных фото;
- явные статусы «Черновик» и «Опубликовано для родителя»;
- публикация отчёта включает подтверждение, генерацию PDF и понятное состояние ошибки/повтора.

## 11. Совместимость и миграция

- Старые данные не удаляются.
- Существующие отчёты не публикуются автоматически.
- Существующие контакты продолжают работать без email.
- Существующая авторизация специалиста и расписание сохраняются.
- Новые frontend assets добавляются в:
  - `.github/workflows/deploy-fizira-frontend.yml`;
  - `ops/release/audit-production-source.sh`;
  - frontend test paths и production audit.
- Новая SQL-миграция будет отдельной и идемпотентной; до её применения frontend не активирует родительский контур.

## 12. Тестирование

Только фиктивные данные:
- ребёнок: Артём Смирнов, 15.04.2020;
- родитель: Анна Смирнова;
- специалист: тестовый специалист;
- занятия, отчёты, цели, оценки, тестовые изображения.

Обязательные тесты:
1. unit: токены/статусы, форматирование дат, safe parent projections;
2. SQL/RLS: parent A не видит child B, source tables и storage недоступны напрямую;
3. Edge Function: истёкшее/повторное/отозванное приглашение; несовпадающий email; PDF/файл чужого ребёнка;
4. UI: приглашение → пароль/согласия → dashboard → расписание → отчёт → фото → цели → динамика → профиль → выход → повторный вход;
5. specialist: приглашение, повтор, отзыв, публикация/снятие публикации, уведомления;
6. regression: текущий кабинет специалиста, расписание, медиа, восстановление пароля и legal acceptance.

До релиза требуется выполнить E2E в отдельном тестовом окружении/тестовом аккаунте без реальных пациентов. Production-проверка должна быть read-only, кроме отдельного явно согласованного тестового набора.

## 13. Критерии готовности

Критерий выполнен, когда:
- родитель регистрируется только по валидному приглашению;
- родитель видит только назначенных детей и опубликованные данные;
- попытки подменить ID, report ID, media ID и URL не дают доступ к чужим данным;
- специалист контролирует публикацию и отзыв доступа;
- есть рабочие просмотр/скачивание PDF;
- интерфейс корректен на мобильном экране;
- все тесты проходят, а production deploy не затрагивает БД и реальные данные.
