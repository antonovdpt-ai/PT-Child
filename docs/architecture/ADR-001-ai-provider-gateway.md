# ADR-001: провайдер-независимый ИИ-контур Fizira

Статус: предложено к проверке  
Дата: 2026-09-19

## Решение

Клиент Fizira не обращается напрямую ни к OpenAI, ни к другому поставщику моделей. Все ИИ-запросы идут через серверный `ai-gateway` в российском контуре. Поставщик и модель выбираются конфигурацией на сервере.

Это не означает автоматический перенос медицинских и персональных данных поставщику. До любого внешнего вызова сервер:

1. авторизует специалиста и проверяет доступ к пациенту;
2. собирает только минимально необходимый контекст;
3. удаляет прямые идентификаторы и выявляет косвенные идентификаторы;
4. блокирует запрос, если безопасное обезличивание не доказано;
5. валидирует запрос по схеме и назначению;
6. журналирует метаданные без исходного клинического текста;
7. отправляет запрос выбранному адаптеру;
8. валидирует структурированный ответ;
9. сохраняет результат как черновик, требующий подтверждения специалистом.

## Почему не делаем немедленную замену OpenAI

Доступность сервиса из РФ не равна пригодности для данных детей и сведений о здоровье. Выбор должен пройти три независимые проверки:

- договор, территория обработки, хранение и логирование запросов;
- технические возможности API и отказоустойчивость;
- качество на реальных задачах Fizira без передачи реальных данных.

На 19.09.2026 в shortlist входят Yandex AI Studio и GigaChat API. Финальный выбор не сделан. OpenAI не считается допустимым production-провайдером для российского запуска, пока не доказана разрешённая схема использования.

## Контракт шлюза

Вход:

```json
{
  "operation": "clinical_summary | session_plan | parent_report | document_extract",
  "patient_ref": "server-side opaque id",
  "input": {},
  "request_id": "uuid"
}
```

Выход:

```json
{
  "request_id": "uuid",
  "provider": "configured-server-side",
  "model": "configured-server-side",
  "status": "draft",
  "result": {},
  "warnings": []
}
```

Клиент не передаёт имя поставщика, модель, системный prompt, API-ключ или произвольный URL.

## Адаптер

Каждый адаптер реализует единый интерфейс:

- `generateStructured(operation, redactedPayload, schema)`;
- таймаут и отмену;
- нормализацию ошибок;
- schema validation;
- ограниченный retry только для безопасных повторов;
- метрики длительности, токенов и ошибок без текста пациента;
- `healthCheck()`.

## Аварийные режимы

- `AI_ENABLED=false`: приложение сохраняет основные клинические функции без ИИ.
- Ошибка обезличивания: fail closed, внешний вызов не выполняется.
- Ошибка модели: пользователь получает повторяемое сообщение; черновик не сохраняется как готовый результат.
- Смена провайдера: только серверная конфигурация после регрессионного теста.

## Проверка кандидатов

Составить обезличенный эталонный набор минимум из 30 сценариев:

- физиотерапевтическое заключение;
- план следующего занятия;
- понятный родителю отчёт;
- извлечение текста из документов;
- случаи с противоречивыми данными;
- запросы с прямыми и косвенными идентификаторами.

Оценивать вслепую двумя специалистами: клиническая корректность, полнота, выдуманные факты, структура JSON, русский язык, время ответа и стоимость. Кандидат не допускается, если добавляет диагнозы/рекомендации без основания или нарушает схему ответа.

## Блокеры до реализации

- инвентаризация существующей Edge Function `ptchild-ai`;
- карта фактических данных для каждой ИИ-операции;
- решение по договору и обработке сведений о здоровье;
- подтверждение места хранения запросов и возможности отключения логирования;
- тест доступа к API с Timeweb;
- эталонный набор и критерии приёмки.

## Критерий готовности

Production использует один проверенный адаптер, второй может быть выключенным резервом. OpenAI полностью удалён из production-конфигурации либо явно отключён. Ни один запрос не уходит наружу до прохождения серверной политики минимизации и обезличивания.
